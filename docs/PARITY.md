# AttendFlow → desktop app parity checklist

The Rust engine crate is in progress at `crates/attend-engine`. All 56 source fixtures
now have generic-mode output goldens generated by replaying AttendFlow's mounted
Meeting surface and reading Dexie after its debounced flush. The Rust semantic harness
currently fails on known implementation gaps; goldens are not yet parity proof. Roster
mode golden replay and upstream test-for-test coverage are still outstanding. See the
crate README and `tests/parity/generator/README.md` for details.

Source: AttendFlow `main` @ 405abd5 (inventory 2026-11-17). Phase column: P1 / P2 / P3,
**N/A** = exists only because of Zoom Apps constraints (replaced by a simpler mechanism),
**OFF** = feature-flagged off in AttendFlow's `mvp` build (optional, P3).

## Parity run status (2026-11-17)

The 56 generic-mode goldens are present and the all-fixture Rust comparison is active.
The adapter seeds the first recorded startup roster responses at the AttendFlow replay
reference time, applies later paired meeting/waiting-room snapshots as roster
replacements, and handles `putFromMainMeeting` as a leave plus waiting-room movement.
Bridge user events also update the live roster. The latest comparison passes 33
fixtures; 23 still have field-level mismatches. The remaining Zoom Apps snapshot
differences trace to AttendFlow applying the roster observation before each debounced
event batch (`Meeting.svelte:421–470`, `repository.ts:2386–2519`), including name
changes discovered by roster diff (`Meeting.svelte:559–591`). Join/rejoin identity
resolution still needs the same batch-level active roster when `appendSessionEvents`
resolves UUIDs (`repository.ts:2410–2470`). The legacy fixtures without `startedAt`
also need their older metadata and late-threshold handling matched. No fixtures are
allow-listed. Roster-mode replay output and the upstream `session-engine.test.ts`,
attendance-status, score, name-utils, and profile-patterns test suites remain
unported. Per-fixture results are regenerated by the test and listed in
[`crates/attend-engine/tests/parity/PARITY-RESULTS.md`](../crates/attend-engine/tests/parity/PARITY-RESULTS.md).

## Not carried over (by design)

| AttendFlow mechanism | Why / replacement |
|---|---|
| Main ↔ Meeting postMessage sync, heartbeat, fallback closure, sessionRevision/ack/cleanup | one process, one store |
| Alias mutation outbox + Sync Review | single writer: decisions write aliases directly (same validation rules) |
| Separate Dexie DBs, orphaned-session cleanup | SQLite in the companion; one record per meeting instance |
| Remote download worker + download center | native/browser download from the local server |
| Install page, Firebase | not needed |
| Host/co-host gating, limited mode | Plugin SDK works as attendee |
| Mid-meeting reload splits records | companion keeps the instance; UI reload resumes |

## Plugin-SDK extras (P3)

Background capture without UI; real join times from meeting start; waiting-room view +
admit / auto-admit roster matches (host); raised-hand state at connect; unknown-arrival
alerts; meeting history across restarts; OFF features (special participants, blacklist
