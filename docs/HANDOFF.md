## 5. Interfaces for the participant / chat investigation

- `Session::participants(Default)` → `IMeetingToolkit::GetParticipantsList()` (sync, SDK-owned vector, copied).

## 7. Known limitations / problems

- SDK runtime must be beside the exe (silent failure otherwise) — `scripts\build.ps1` handles it; plain `cargo build` alone does **not** sync it (use the script, or `doctor` will flag it).
- Marketplace: plain "OAuth redirect URL" rejects loopback/localhost; only the **PKCE OAuth Redirect URL** field accepts `127.0.0.1`, and only the **public client ID** receives it. Loopback redirects may be rejected at Marketplace publishing review (dev only).
- PSDKTest project targets v142; we override to v143 on the command line.
- SDK is process-global: one `Session` per process.
- `OnIPCConnectStatusChanged` error text encoding undocumented (treated as UTF-8, lossy).
- Every bridge query has a 30 s timeout; synchronous SDK calls run on the SDK thread.
- Cargo 1.100 uses a new build-dir layout (test exes under `target\debug\build\...`); don't rely on `OUT_DIR` ancestry.

## 9. Local companion server

`serve` owns one long-lived Plugin SDK session and exposes the protocol in
[BRIDGE-PROTOCOL.md](BRIDGE-PROTOCOL.md). It binds only to loopback:

```powershell
$env:ZOOM_PLUGIN_SDK_DIR = 'C:\path\to\zoom-plugin-sdk-windows-7.2.0.3001\x64'
.\scripts\build.ps1
.\scripts\run.ps1 serve
.\scripts\run.ps1 serve --port 47812 --ui C:\path\to\attendflow\dist --open
.\scripts\run.ps1 serve --allow-origin http://localhost:5173
```

Default HTTP/WebSocket endpoint is `127.0.0.1:47812` and `/bridge`. With
no `--ui`, the root serves a live status page. `Ctrl+C` flushes the meeting
JSONL and shuts down the SDK session. Per-instance logs and `current.json`
are written to `%LOCALAPPDATA%\zoom-companion\meetings\`; a matching meeting
can resume for 15 minutes after a process restart.

### AttendFlow Desktop

`scripts\build.ps1` runs `pnpm install --frozen-lockfile` and builds
`apps\desktop-ui`, then copies it into `target\debug\ui` (or `target\release\ui`).
`scripts\package.ps1` includes `ui\` beside the release executable. Run
`zoom-companion app` to open the native **AttendFlow Desktop** WebView2 window;
closing the window exits. Use `zoom-companion serve --fake --ui apps\desktop-ui\dist`
for UI/API work that must not initialize the SDK. `pnpm dev` proxies `/api` and
`/bridge` to `127.0.0.1:47812`; run the server with
`--allow-origin http://localhost:5173` for that development origin.
The fake mode seeds a two-person demo meeting in a process-specific temp folder and
does not touch the normal application database or start an SDK session.

SQLite data lives at `%LOCALAPPDATA%\zoom-companion\data.db`; the existing
`%LOCALAPPDATA%\zoom-companion\meetings\*.jsonl` files remain the append-only
event backup and are imported idempotently when the server starts. Config docs
and meeting states are revisioned. The desktop record endpoint now uses
`EngineRecordProvider` backed by `crates\attend-engine`; the stub remains available
for tests. Ingestion produces an AttendFlow-shaped SessionRecord and derives rows
and summary through the same engine path as the parity fixtures.

### In-meeting experiment console

Use `lab` only in an owner-controlled test meeting. It authenticates/attaches to
Zoom Workplace, logs every event and command result as JSONL, and prints a
join/leave ledger when exiting. Set `ZOOM_PLUGIN_SDK_DIR` to the x64 SDK root

```powershell

.\scripts\run.ps1 lab --script .\experiment.txt
```

`poll <seconds>`, `note <text>`, `sleep <seconds>` (non-blocking: events, ledger

### Name matching panel implementation (2026-11-17)

The roster-mode live view has a Name Matching panel with pending participant cards,
quick candidate match / guest / shared-name actions, a searchable manual roster match,
split-person selection, name-change decisions, resolved decision labels, and Revert.
The matching navigation badge counts unmatched rows and undecided name-change events;
the Ignored summary opens the panel. Record detail uses the same component read-only.

Decisions are stored in revisioned meeting state as `reconciliationDecisions` using
AttendFlow action names. `/api/meetings/:id/reconciliation` applies match alias
upserts or guest/split alias removals in the same SQLite transaction as the state
write. Alias validation rejects canonical-name and cross-person nickname conflicts
before either document changes. Revert removes the decision and leaves aliases in
place. A stale revision returns 409 for the UI's single refetch-and-retry attempt.
The record endpoint derives rows from the updated state and emits `record_updated`.

Verification: `scripts/test.ps1` passed, including roster derivation parity (448
variants), general parity (56 records), 29 companion tests, and the companion
self-test. The Name Matching component tests were added but `pnpm check` / `pnpm
build` could not run in this worktree because `node_modules` is absent and the
locked Svelte package tarball is not cached for offline installation. No SDK
session was started.

### Record detail activity and exports (2026-11-17)

The desktop UI reuses `RecordActivity` in live and record views for overview,
auto-attendance filters/sorting, read-only matching, settings, name changes,
entry/exit events, raise-hand activity, and manual snapshots. Manual snapshots
store participant identity, meeting/waiting-room location, and current match
status. Raise/lower callbacks are deduplicated by state transition; the initial
participant snapshot preserves hands that were already raised when observation
began. Captures require at least one currently raised hand.

Record exports are generated by the companion in one Rust module. JSON bundles
use `{version: 3, exportedAt, session}`; summary and manual-record CSVs use
AttendFlow headers and UTF-8 BOMs, with waiting-room minutes appended to summary
CSV. Downloading updates the revisioned state and records-list status.

Verification: `scripts/test.ps1` passed (79 Rust tests, one informational ignored
Zoom-Apps ingestion test, plus companion self-test); `pnpm check` passed with 0
errors and 0 warnings; `pnpm test --run` passed 13 tests in 6 files; `pnpm build`
passed. No real SDK session was started.
