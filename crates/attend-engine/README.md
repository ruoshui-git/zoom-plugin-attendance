# attend-engine

Pure Rust attendance domain crate. It has no SDK, storage, HTTP, or FFI dependency.
All public configuration, event, row, and record types use serde camelCase JSON so
AttendFlow roster/profile/alias and record-shaped values can be deserialized directly.

## Public API

- `adapt_bridge_events` maps bridge v1 events to the normalized event stream. It uses
  `<instanceId>:<userId>` participant UUIDs and preserves waiting-room location.
- `adapt_zoom_apps_events` maps AttendFlow recording fixture events into the same stream.
- `adapt_bridge_events` / `adapt_zoom_apps_events` normalize source events. `build_record`
  currently combines ingestion and derivation for legacy callers.
- `derive(&SessionRecord, &EngineConfig, decisions, reference_time, &EngineOptions)` is
  the AttendFlow-shaped derivation entry point; `Derived` returns rows and summary.
  Its SessionRecord schema includes participant history, movement/name changes, roster
  observations, manual snapshots, decisions, and raise-hand data.
- `normalize_name`, `build_pinyin`, `candidate_people`, `profile_includes_group`,
  `select_profile`, and `score` are available independently.
- `EngineOptions::default()` applies the companion policy. Use
  `EngineOptions::attendflow_compat()` for AttendFlow waiting-room behavior.

## Deliberate behavior differences

By default, waiting-room time is excluded from attendance minutes and first-join/late
calculations, and is reported as `waitingRoomMinutes` with `firstWaitingRoomAt`.
Compatibility mode counts it as presence. The engine ignores events after
`instance_ended`; it does not open a replacement record.

## Fixture assets and verification

`tests/parity/fixtures/` contains 56 copied AttendFlow source recordings.
`tests/parity/goldens/` contains output captured from AttendFlow's real mounted
`Meeting.svelte` pipeline and Dexie after playback and the debounced flush. Each file
now includes the full final SessionRecord, exact derivation reference time, generic
rows/summary, and eight roster variants (zh/en example config × match/guest/split/
name-change-keep-match). The re-runnable upstream generator is documented in
`tests/parity/generator/README.md`.

The Zoom-Apps semantic comparison remains `#[ignore]`d and informational (33/56 in
the current report); it is not the desktop app's correctness gate. The required hard
gate is derivation from each captured SessionRecord, independently of Zoom-Apps
batching. The current Rust derive API and golden schema are in place, but exact 56/56
row parity, roster-variant parity, the full upstream test port, and the complete
companion scenario suite are not yet complete. No mismatches are allow-listed. See
`docs/PARITY.md` for the remaining gaps.

`tests/parity/pinyin-goldens.json` contains 3,500 consecutive CJK characters starting
at U+4E00 plus 283 unique fixture/example-config names, with outputs generated by
`tiny-pinyin`. Raw `pinyin` crate output differed on 142/3,783 values (3.7536%): five
fixture/config names and 137 individual characters. The five full-name differences
are covered by `src/pinyin_overrides.json`; the Rust test confirms exact output for all
multi-character fixture/config entries. Character-level mismatches remain and should
be reported if callers search individual characters.

To regenerate source fixtures, copy the three directories from the reference snapshot
into `tests/parity/fixtures/`. Run the generator script against the clean AttendFlow
snapshot to replay every recording and replace generic-mode goldens. The script copies
its temporary Vitest into that snapshot and deletes it afterward; it does not modify
tracked upstream files.

## Companion stream scenario catalogue

Bridge streams use Plugin SDK semantics: IDs are instance-scoped and change on rejoin;
admission is a waiting-room leave followed by an in-meeting add; renames are updates
with the same ID; periodic/manual snapshots arrive as `users sync_all`. The current
scenario tests exercise the rows marked Tested below. The remaining named cases are
required follow-up coverage and are not yet part of the Rust suite.

| AttendFlow fixture scenario | Companion stream expectation | Coverage |
|---|---|---|
| Admit from waiting room | `add(waiting)` → `left(waiting)` → `add(meeting,new ID)`; one identity | Tested |
| Direct join/leave | One session participant and a left row | Partial |
| Duplicate display names | Simultaneous same-name IDs remain distinct and ambiguous | Tested |
| Leave then rejoin same name | New ID stitches to the inactive identity | Tested |
| Repeated rejoin | Each changed ID joins the same inactive identity | Not yet tested |
| Rename while present / after rejoin / in waiting room | `update` retains ID, changes name, creates no movement | Partial |
| Move to waiting room and back | Old meeting ID leaves; waiting ID admitted under same identity | Not yet tested |
| Waiting-room leave without admit | No first meeting join or presence minutes | Tested |
| Burst joins/leaves | All IDs and exits survive a burst before snapshot | Partial |
| Guests | Unmatched generic attendance remains visible | Not yet tested |
| Many participants | Snapshot and event stream preserve each identity | Partial |
| Meeting end with active participants | Later events do not continue the ended instance | Tested |
| Manual snapshot | `sync_all` replaces the live roster without inventing joins | Partial |
| Raise hand | Raise/lower entries follow the participant UUID | Partial |
