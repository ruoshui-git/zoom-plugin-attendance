# attend-engine

Pure Rust attendance domain crate. It has no SDK, storage, HTTP, or FFI dependency.
All public configuration, event, row, and record types use serde camelCase JSON so
AttendFlow roster/profile/alias and record-shaped values can be deserialized directly.

## Public API

- `adapt_bridge_events` maps bridge v1 events to the normalized event stream. It uses
  `<instanceId>:<userId>` participant UUIDs and preserves waiting-room location.
- `adapt_zoom_apps_events` maps AttendFlow recording fixture events into the same stream.
- `build_record(meta, events, config, state, options, now)` derives participants,
  movement and rename events, latest roster, rows, summary, and raise-hand entries.
- `normalize_name`, `build_pinyin`, `candidate_people`, `profile_includes_group`,
  `select_profile`, and `score` are available independently.
- `EngineOptions::default()` applies the companion policy. Use
  `EngineOptions::attendflow_compat()` for AttendFlow waiting-room behavior.

## Deliberate behavior differences

By default, waiting-room time is excluded from attendance minutes and first-join/late
calculations, and is reported as `waitingRoomMinutes` with `firstWaitingRoomAt`.
Compatibility mode counts it as presence. The engine ignores events after
`instance_ended`; it does not open a replacement record.

## Fixture assets and verification

`tests/parity/fixtures/` contains the copied AttendFlow source JSON from
`src/lib/__tests__/{fixtures,zoomsdk-recordings,zoomsdk-recordings-1}`. Run
`cargo test -p attend-engine` to validate the copied input inventory, adapters, and
engine unit tests. The current fixture test verifies that all 56 copied JSON inputs
parse and adapt. It is an input-integrity check, not a per-fixture output golden
comparison. Real-pipeline AttendFlow output goldens, generic/roster replay coverage,
and the port of all upstream session-engine tests remain follow-up parity work; this
README does not claim those acceptance gates have passed.

`tests/parity/pinyin-goldens.json` contains 3,500 consecutive CJK characters starting
at U+4E00 plus 283 unique fixture/example-config names, with outputs generated by
`tiny-pinyin`. Raw `pinyin` crate output differed on 142/3,783 values (3.7536%): five
fixture/config names and 137 individual characters. The five full-name differences
are covered by `src/pinyin_overrides.json`; the Rust test confirms exact output for all
multi-character fixture/config entries. Character-level mismatches remain and should
be reported if callers search individual characters.

To regenerate source fixtures, copy the three directories from the reference snapshot
into `tests/parity/fixtures/`. Generate output goldens by replaying each source fixture
through AttendFlow's recording helpers and repository pipeline, serializing the final
`SessionRecord` fields named in `docs/PARITY.md`; then compare semantically in Rust.
Do not edit the upstream clean snapshot except for temporary, untracked generator tests.
